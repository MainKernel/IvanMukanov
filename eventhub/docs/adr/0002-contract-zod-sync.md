# ADR-0002: Захист від розходження обмежень між OpenAPI-контрактом і Zod-схемами

## Статус

Прийнято · 2026-11-05

## Контекст

У пакеті `@eventhub/contracts` співіснують два артефакти, що описують одні й ті самі правила вхідних даних:

1. **`openapi.yaml`** — декларативна специфікація API (використовується для документації, генерації TypeScript-типів через `openapi-typescript` та мок-сервера Prism).
2. **`src/schemas.ts`** — виконувані Zod-схеми (`listEventsQuery`, `createOrderBody` тощо), якими `ZodValidationPipe` валідує та коерсить (`z.coerce.number()`) вхідні HTTP-запити в `api-gateway`.

Через те, що TypeScript стирає числові межі до базового типу `number` (`minimum: 1, maximum: 50` у `schema.ts` перетворюється просто на `limit?: number`), виникає ризик **тихого розходження (Contract Drift)**:

- Розробник змінює `maximum: 50` на `maximum: 100` в `openapi.yaml`, але забуває оновити `.max(50)` у `schemas.ts` (або навпаки).
- `openapi-typescript` генерує той самий тип `number`, тому `tsc --noEmit` проходить без жодної помилки.
- На мок-сервері Prism запит `?limit=80` повертає `200 OK`, а на продакшн-бекенді падає з `400 Bad Request`.

Потрібен механізм, який гарантує, що будь-яке розходження між правилами `openapi.yaml` та `schemas.ts` **негайно ламає збірку (`pnpm build`)**.

## Розглянуті варіанти

### Варіант A. Генерація Zod-схем зі специфікації (`openapi-zod-client` / `orval`)

Зробити `openapi.yaml` єдиним джерелом і генерувати `schemas.ts` автоматично під час `pnpm generate`.

- **Плюси:**
  - повна відсутність ручного дублювання;
  - зміна `maximum` у YAML автоматично потрапляє в Zod-схему.
- **Мінуси:**
  - генератори погано підтримують специфіку нашого домену: наприклад, стандартний `z.string().uuid()` відхиляє наші UUIDv7 у деяких конфігураціях, тому в `schemas.ts` потрібен кастомний регулярний вираз `uuidLike` та українські повідомлення про помилки;
  - для query-параметрів у NestJS потрібна коерсія рядків у числа (`z.coerce.number()`), тоді як більшість генераторів створюють звичайний `z.number()`, який падає на рядках із `req.query`;
  - важка зовнішня залежність із власним циклом оновлень і обмеженою підтримкою OpenAPI 3.1.

### Варіант B. Code-first: генерація `openapi.yaml` із Zod-схем (`@asteasolutions/zod-to-openapi`)

Писати лише Zod-схеми в TypeScript, а `openapi.yaml` генерувати з них скриптом.

- **Плюси:**
  - єдине джерело правди у TypeScript;
  - повний контроль над `z.coerce`, кастомними regex та текстами помилок.
- **Мінуси:**
  - руйнує прийнятий у курсі підхід **Design-First**: специфікація перестає бути первинним документом, який можна узгодити в команді до написання коду;
  - опис іменованих прикладів (`examples.filled`, `examples.empty`), RFC 9457 `Problem` і розгорнутих коментарів-обґрунтувань у TypeScript-коді стає громіздким і нечитабельним порівняно з YAML.

### Варіант C. Чисто тип-рівнева перевірка (`z.infer` проти `openapi-typescript`)

Додати у `schemas.ts` перевірку сумісності типів `AssertStructuralMatch<z.infer<typeof schema>, OpenApiType>`.

- **Плюси:**
  - нуль додаткових інструментів, працює миттєво під час `tsc --noEmit` прямо в IDE;
  - миттєво ловить перейменування полів, пропущені обов'язкові параметри або зміну типу (`string` ↔ `number`).
- **Мінуси:**
  - **не вирішує проблему числових меж (`maximum: 50`)**: для `openapi-typescript` і `minimum: 1, maximum: 50`, і `minimum: 1, maximum: 999` мають однаковий тип `number`. Без модифікації генератора типів така перевірка не помітить зміни `50` на `40`.

### Варіант D. Комбінована верифікація на етапі збірки (Type-level Check + Build-time Boundary Verifier)

Зберегти `openapi.yaml` первинним контрактом і рукописні Zod-схеми з кастомною коерсією, але вбудувати у `pnpm build` пакета `@eventhub/contracts` двоступеневий контроль:

1. **На рівні типів (`src/schemas.ts`)** — `AssertStructuralMatch` звіряє структуру та обов'язковість полів кожного `z.infer<...>` із типами `paths` та `components` зі згенерованого `schema.ts`.
2. **На рівні значень (`scripts/verify-constraints.mjs`)** — скрипт збірки витягує числові обмеження (`minimum`, `maximum`, `default`) напряму з `openapi.yaml` і проганяє граничні точки (`min - 1`, `min`, `max`, `max + 1`, `default`) через скомпільовані Zod-схеми (`safeParse`). При найменшому розходженні `pnpm build` завершується з кодом `1`.

- **Плюси:**
  - зберігає чистий Design-First (`openapi.yaml` залишається людиночитаним джерелом правди);
  - зберігає гнучкість рукописних Zod-схем (`z.coerce.number()`, підтримка UUIDv7, локалізовані повідомлення);
  - гарантовано ламає `pnpm build` як при структурних змінах (через `tsc`), так і при зміні числових меж `minimum` / `maximum` / `default` (через `verify-constraints.mjs`);
  - не потребує жодної сторонньої бібліотеки (працює на чистому Node.js).
- **Мінуси:**
  - при зміні ліміту значення все ще потрібно оновити у двох місцях (`openapi.yaml` та `schemas.ts`), хоча забути про друге місце тепер неможливо — збірка одразу впаде з точним вказанням поля та очікуваної межі;
  - при додаванні нових ендпоїнтів із числовими обмеженнями правило перевірки потрібно реєструвати у `verify-constraints.mjs`.

## Рішення

Обрано **Варіант D**: двоступеневу верифікацію контракту в пакеті `@eventhub/contracts`, що поєднує compile-time перевірку структури типів (`AssertStructuralMatch` у [`src/schemas.ts`](../../packages/contracts/src/schemas.ts)) та автоматичний build-time верифікатор граничних значень ([`scripts/verify-constraints.mjs`](../../packages/contracts/scripts/verify-constraints.mjs)), вбудований у скрипт `build` пакета `@eventhub/contracts`.

## Наслідки

### Позитивні

- Розбіжність між `maximum: 50` в `openapi.yaml` та `.max(50)` у `schemas.ts` неможливо пропустити на продакшн: `pnpm build` падає з чіткою діагностикою.
- Зміна назви або обов'язковості параметра в `openapi.yaml` одразу підсвічується червоним у редакторі та ламає `pnpm typecheck`.
- Turborepo кешує результат верифікації разом із задачею `@eventhub/contracts#build` і автоматично перезапускає її при будь-якій зміні `openapi.yaml` або `src/schemas.ts`.

### Негативні й компроміси

- Залишається необхідність редагувати два файли при свідомій зміні бізнес-ліміту (компенсується тим, що CI/збірка вкаже точне місце невідповідності).
- Скрипт `verify-constraints.mjs` покладається на регулярну структуру оголошення параметрів у `openapi.yaml` і потребує розширення при появі нових типів обмежень (наприклад, `minLength` / `maxLength` для рядків).
- Додає ~30 мс до часу виконання `pnpm --filter @eventhub/contracts build` (при cache miss).
