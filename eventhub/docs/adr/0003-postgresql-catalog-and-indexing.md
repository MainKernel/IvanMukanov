# ADR-0003: Схема каталогу в PostgreSQL, складений індекс пагінації та ізоляція Prisma-моделі

## Статус

Прийнято · 2026-11-05

## Контекст

У тижні 2 каталог подій зберігався у пам'яті процесу (`EVENTS` у `seed.ts`). При переході на реляційну СКБД **PostgreSQL 17** постали чотири архітектурні питання, які дорого змінювати після накопичення даних і появи суміжних сервісів:

1. **Інструмент доступу до БД та межа шару репозиторію:** як працювати з PostgreSQL у TypeScript-монорепозиторії без витоку типів бази даних у контролери та публічний HTTP-контракт (`@eventhub/contracts`).
2. **Фізичне представлення грошей і часу в схемі БД:** у контракті ціна передається вкладеним об'єктом `Money { amount, currency }`, а час — рядком ISO 8601.
3. **Забезпечення швидкодії курсорної пагінації (`ADR-0001`):** запит `ORDER BY "startsAt" ASC, "id" ASC LIMIT 21` із предикатом `(startsAt, id) > (:afterStartsAt, :afterId)` на великих обсягах даних не повинен виконувати повне сканування таблиці (`Seq Scan`) і сортування в пам'яті (`top-N heapsort`).
4. **Завантаження пов'язаного майданчика (`Venue`):** кожна подія у відповіді містить вкладений об'єкт `venue`, що створює ризик проблеми **N+1 запитів**.

## Розглянуті варіанти

### Варіант A. Сирий SQL (`pg`) або легкий конструктор запитів (`Kysely`) без ORM-міграцій

Писати SQL-запити та DDL-міграції вручну, мапити рядки `pg` безпосередньо у доменні типи.

- **Плюси:**
  - повний контроль над SQL, включаючи кортежне порівняння `("startsAt", "id") > ($1, $2)`;
  - мінімальний розмір бандла та відсутність бінарного рушія запитів.
- **Мінуси:**
  - відсутність єдиної декларативної схеми з автоматичною генерацією міграцій та перевіркою узгодженості типів таблиць і запитів на етапі компіляції без додаткової кодогенерації;
  - вищий поріг супроводу при додаванні таблиць місць (`Seat`) та замовлень.

### Варіант B. Prisma ORM із прямим поверненням моделей клієнта з репозиторію

Використовувати `PrismaClient`, але повертати результат `prisma.event.findMany({ include: { venue: true } })` напряму з `EventRepository` у `CatalogService` та контролер.

- **Плюси:**
  - мінімум шаблонного коду (не потрібен мапер `toEvent`).
- **Мінуси:**
  - **порушення контракту API (`@eventhub/contracts`):** у таблиці `Event` гроші зберігаються двома колонками (`minPriceCents: Int`, `currency: Char(3)`), а час має тип `Date`. Пряма серіалізація результату Prisma зламає контракт (`minPrice: { amount, currency }`), поверне зайві службові поля (`venueId`, `createdAt`) та непробілоочищений `CHAR(3)`;
  - жорстка прив'язка бізнес-логіки (`CatalogService`) до внутрішньої структури таблиць PostgreSQL.

### Варіант C. Prisma ORM + явний доменний мапер `toEvent` + складений індекс `@@index([startsAt, id])`

Використовувати Prisma (`^6.19.3`) для декларативної схеми (`schema.prisma`), міграцій і типобезпечних запитів, але суворо ізолювати Prisma всередині `EventRepository`:

1. **Фізична схема даних:**
   - Гроші зберігаються у копійках (`minPriceCents Int`, `priceCents Int`) та `currency String @db.Char(3)` — жодних `FLOAT`/`DOUBLE`, де `0.1 + 0.2 !== 0.3`.
   - Час зберігається як ` TIMESTAMPTZ(3)` (`@db.Timestamptz(3)`), що примусово нормалізує значення до UTC з точністю до мілісекунд.
   - Цілісність місць у межах події гарантується складеним унікальним обмеженням `@@unique([eventId, rowLabel, number])` на рівні БД.
2. **Складений B-Tree індекс `@@index([startsAt, id])`:** порядок колонок в індексі точно повторює `ORDER BY "startsAt" ASC, "id" ASC` та предикат курсора з `ADR-0001`.
3. **Завантаження зв'язків:** обов'язкове використання `include: { venue: true }`, яке Prisma виконує за фіксовану кількість запитів замість циклу з `N+1` звернень.
4. **Доменний мапер `toEvent(row: EventRow): Event`:** перетворює рядок БД на тип `Event` із `@eventhub/contracts` (конвертує `Date` → ISO-рядок, групує `minPriceCents` + `currency.trim()` у `Money`, відкидає `venueId`).

## Рішення

Обрано **Варіант C**.

Результати емпіричної перевірки на таблиці з **100 010 подіями** (`pnpm --filter @eventhub/api-gateway db:bench`):

- **Зі складеним індексом `Event_startsAt_id_idx` (`("startsAt", "id")`):**
  планувальник PostgreSQL використовує `Index Scan using "Event_startsAt_id_idx" on "Event"`, читає рівно 21 рядок і завершує запит за **0.052 ms** (`cost=0.42..2.86`).
- **Без індексу:**
  планувальник змушений виконувати `Parallel Seq Scan on "Event"` по всіх 100 010 рядках із подальшим сортуванням `Sort (top-N heapsort)`, що займає **9.488 ms** (`cost=5217.49..5219.91`) — у **~182 рази повільніше** на 100 тис. рядків і деградує лінійно $O(N)$ зі зростанням таблиці.
- **Проблема N+1 (`PRISMA_LOG=query`):**
  запит сторінки з 20 подій із `include: { venue: true }` генерує рівно **1 SQL-запит** (або 2 при `IN (...)` залежно від стратегії), тоді як довантаження майданчика в циклі породжує **21 окремий запит** (`1 + 20`).

## Наслідки

### Позитивні

- **Нуль змін вище репозиторію:** перехід із масиву в пам'яті на PostgreSQL не змінив жодного рядка у `CatalogService`, `CatalogController` чи `@eventhub/contracts`.
- **Стабільний час відповіді $O(\log N)$:** завдяки індексу `("startsAt", "id")` вибірка сторінки каталогу займає долі мілісекунди незалежно від того, чи в базі 10 подій, чи 100 000.
- **Фінансова та часова точність:** зберігання цін у цілих копійках (`Int`) та дат у `TIMESTAMPTZ(3)` унеможливлює помилки округлення та зсуви часових поясів.
- **Ідемпотентність та детермінованість сидів:** `prisma/seed.ts` використовує `upsert` за фіксованими UUID для майданчиків і подій та детерміноване перестворення 800 місць (`deleteMany` + `createMany`), що дозволяє безпечно запускати `db:seed` повторно.

### Негативні й компроміси

- **Накладні витрати на підтримання складеного індексу при записі:** кожен `INSERT` або `UPDATE` поля `startsAt` у таблиці `Event` оновлює B-Tree індекс `Event_startsAt_id_idx`. Для каталогу подій, де читання переважає запис на порядки (read-heavy), цей компроміс повністю виправданий.
- **Денормалізований лічильник `availableSeats` у таблиці `Event`:** дозволяє віддавати список подій без агрегації `COUNT(*)` по таблиці `Seat` на кожному запиті каталогу, але вимагає транзакційного оновлення під час бронювання місць у наступних роботах, щоб уникнути розсинхронізації.
- **Розширене представлення курсорного предиката в Prisma:** оскільки Prisma `where` не підтримує компактний SQL-кортеж `("startsAt", "id") > ($1, $2)` напряму у типізованому фільтрі, предикат записується через еквівалентну диз'юнкцію `OR: [{ startsAt: { gt } }, { startsAt: equals, id: { gt } }]`.
