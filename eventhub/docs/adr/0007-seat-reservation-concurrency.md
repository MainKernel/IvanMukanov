# ADR-0007: Стратегія конкурентності при резерві місць

- **Статус:** Прийнято
- **Дата:** 2026-11-06

## Контекст

Під час старту продажів на популярну подію десятки або сотні користувачів одночасно намагаються забронювати одні й ті самі місця. Без належного контролю конкурентності виникають три класи критичних помилок:

1. **Подвійний продаж (double booking / lost update):** якщо застосунок спершу читає стан місця (`findUnique`), перевіряє `if (seat.status !== "FREE")` у коді Node.js і потім виконує `update`, то на типовому для PostgreSQL рівні ізоляції `Read Committed` кілька паралельних запитів бачать місце вільним і продають його кільком покупцям (навіть усередині `$transaction`).
2. **Взаємне блокування (deadlock, `SQLSTATE 40P01`):** якщо два покупці одночасно бронюють перетинні набори місць у різному порядку (`[A-1, A-2]` та `[A-2, A-1]`), транзакції можуть захопити рядкові блокування назустріч одна одній і утворити цикл очікування.
3. **Роз'їзд лічильника `Event.availableSeats` та «завислі» резерви:** якщо покупець закрив вкладку й не оплатив замовлення, місця не повинні залишатися у стані `HELD` назавжди, а повторне повернення місць при скасуванні й фоновому прибиранні не повинно двічі збільшувати `availableSeats`.

Нам потрібно обрати стратегію конкурентного резервування місць у PostgreSQL + Prisma, давши відповідь на три ключові архітектурні питання:
1. Чому обрано атомарний `UPDATE ... WHERE status = 'FREE'` із перевіркою `count`, а не `SELECT ... FOR UPDATE`?
2. Чому залишено рівень ізоляції `Read Committed`, а не використано `Serializable`?
3. Що саме ми втратили, обравши цей шлях?

---

## Рішення

### 1. Чому атомарний `UPDATE` з умовою у `WHERE`, а не `SELECT ... FOR UPDATE`

Резерв місць виконується одним атомарним оператором `updateMany`:

```ts
const seatIds = [...input.seatIds].sort();

const held = await tx.seat.updateMany({
  where: { id: { in: seatIds }, eventId: input.eventId, status: SeatStatus.FREE },
  data: {
    status: SeatStatus.HELD,
    holdExpiresAt: holdUntil,
  },
});

if (held.count !== seatIds.length) {
  throw new SeatsUnavailable(await this.whichAreTaken(tx, seatIds, input.eventId, now, ...));
}
```

**Чому не `SELECT ... FOR UPDATE` + перевірка в JS + `UPDATE`:**
- **Відсутність зайвого мережевого раундтрипу під блокуванням:** під час виконання `UPDATE ... WHERE status = 'FREE'` рушій PostgreSQL сам захоплює рядкові блокування (`FOR NO KEY UPDATE`), при конкурентному звільненні блокування автоматично перечитує актуальну версію рядка та переоцінює предикат `WHERE` (механізм `EvalPlanQual`), і в тій самій операції записує новий стан `HELD`. Між перевіркою умови та зміною стану немає **жодного рядка коду застосунку** і жодного мережевого пересилання даних між БД та Node.js.
- **Менша тривалість утримання рядкового блокування:** у підході `SELECT ... FOR UPDATE` блокування береться під час першого запиту, дані передаються в Node.js, перевіряються в JS, і лише другим запитом відправляється `UPDATE`. Блокування утримується щонайменше на 1 RTT довше.
- **Підтримка на рівні Prisma ORM:** Prisma не має вбудованого типобезпечного методу для `SELECT ... FOR UPDATE` (довелося б писати сирий SQL через `tx.$queryRaw`), тоді як `tx.seat.updateMany` з подальшою перевіркою `held.count !== seatIds.length` повністю типобезпечний і однаковий для всіх переходів станів (`SeatStatus.FREE → HELD`, `OrderStatus.PENDING → CANCELLED`, `OrderStatus.PENDING → EXPIRED`).
- **Попереднє сортування `[...input.seatIds].sort()`:** гарантує канонічний порядок обходу індексу первинного ключа у всіх паралельних транзакціях, роблячи цикл взаємного очікування (`40P01`) неможливим.

### 2. Чому `Read Committed`, а не `Serializable`

Ми свідомо використовуємо стандартний рівень ізоляції PostgreSQL `Read Committed` замість `Serializable` (Serializable Snapshot Isolation, SSI):

- **Відсутність каскадних відмов `40001 (serialization_failure)` на популярній події:** кожне замовлення оновлює спільний рядок події (`UPDATE "Event" SET "availableSeats" = "availableSeats" - N`). У режимі `Serializable` дві паралельні транзакції, що купують **абсолютно різні місця** (наприклад, `A-1` та `H-10`) на одну й ту саму подію, конфліктують на спільному рядку `Event` (та індексних діапазонах `Seat`). У результаті SSI примусово обриває 90%+ легітимних покупок неперетинних місць із помилкою `40001`, вимагаючи складних циклів повторних спроб (retry loops) з експоненційним backoff.
- **Точкова серіалізація через рядкові блокування та атомарний декремент:** у `Read Committed` транзакції, що бронюють різні місця, не заважають одна одній на таблиці `Seat`, а на таблиці `Event` атомарний вираз `{ availableSeats: { decrement: seatIds.length } }` безпечно виконується послідовно на найсвіжішому зафіксованому значенні без втрачених оновлень (lost updates) і без відкату транзакції.

## Наслідки

### Плюси
- **Гарантована відсутність подвійного продажу:** навантажувальний тест `race:test` (50 одночасних запитів на одне місце) стабільно дає рівно один `201 Created`, 49 відповідей `409 Conflict` та жодної `500`.
- **Багаторівневий захист (Defense in Depth):** навіть у разі помилки в коді сервісу унікальний індекс `OrderItem_seatId_key` (`@unique` на `OrderItem.seatId`) фізично не дозволить базі даних створити дві позиції замовлення на одне крісло, а `Order_idempotencyKey_key` захищає від дублювання замовлень при мережевих повторах.
- **Точний баланс `availableSeats`:** як скасування замовлення користувачем (`cancel`), так і фоновий прибиральник (`releaseExpired`) переводять замовлення з `PENDING` атомарним `updateMany` з умовою `status: OrderStatus.PENDING` у `WHERE` і збільшують `availableSeats` рівно на `released.count` фактично звільнених місць.

### Мінуси (що саме ми втратили, обравши цей шлях)
1. **Неможливість захистити міжрядкові інваріанти (write skew) самим лише `WHERE` на рівні `Read Committed`:**
   Обираючи `Read Committed` замість `Serializable`, ми втратили автоматичний захист від аномалій *write skew* та *phantom reads*. Будь-яке бізнес-правило, умова якого залежить від агрегату по кількох рядках (наприклад, «не більше 4 квитків на одного користувача на подію»), не може бути записане в `WHERE` одного `UPDATE` і потребує окремої точки серіалізації (див. розділ нижче).
2. **Короткочасне «фантомне» захоплення частини місць до відкату транзакції:**
   Якщо покупець замовляє два місця `[A-1, A-2]`, де `A-1` вільне, а `A-2` вже зайняте, то `tx.seat.updateMany` спершу захопить рядкове блокування й тимчасово змінить `A-1` на `HELD` у межах поточної транзакції, і лише на кроці `if (held.count !== seatIds.length)` викине `SeatsUnavailable`, що викличе `ROLLBACK`. Протягом цих кількох мілісекунд паралельний покупець, який хоче купити лише `A-1`, буде заблокований до завершення відкату (при `SELECT ... FOR UPDATE NOWAIT` або попередній перевірці можна було б виявити зайнятість `A-2` без модифікації `A-1`).
3. **Втрата детальної діагностики в одному запиті (потреба у `whichAreTaken`):**
   Оскільки `updateMany` у PostgreSQL/Prisma повертає лише кількість змінених рядків (`{ count: number }`), ми втратили інформацію про те, *яке саме* місце з масиву спричинило відмову. Щоб повернути клієнту точний список `seatIds` у тілі `409 Conflict`, на гілці помилки доводиться виконувати додатковий запит `whichAreTaken`.
4. **Необхідність явного кроку `releaseExpired` перед резервом:**
   Через те, що `Event.availableSeats` денормалізовано і зменшується при резерві, ми не можемо просто підставити ліниву умову `availableSeatWhere` (`status = 'FREE' OR (status = 'HELD' AND holdExpiresAt < now)`) у `tx.seat.updateMany`: повторне резервування протермінованого `HELD`-місця вдруге зменшило б `availableSeats`. Тому транзакція створення замовлення змушена перед резервом виконувати Крок 0 (`await this.releaseExpired(tx, now, { eventId })`), що додає накладні витрати на кожне замовлення.
5. **Точка конкуренції (hot row) на рядку `Event`:**
   Оновлення `tx.event.update({ data: { availableSeats: { decrement: seatIds.length } } })` бере ексклюзивне рядкове блокування на рядок події до кінця транзакції (`tx.order.create`). При тисячах одночасних покупок різних місць однієї події всі транзакції шикуються в чергу на рядку `Event`.

## Додаткові архітектурні покращення та розширення (Домашнє завдання, п. 8.4, 15.4, 15.5)

### 1. Складений індекс `@@unique([userId, idempotencyKey])` проти глобального `@unique` (п. 8.4)
У поточній схемі `Order.idempotencyKey` має глобальний `@unique`, тому в `OrdersService.replay` обов'язково виконується перевірка `if (row.userId !== user.id) throw new IdempotencyKeyReused()`.
- **Чому складений індекс `@@unique([userId, idempotencyKey])` кращий:** простір ключів ідемпотентності ізолюється в межах кожного користувача. Один користувач не може (навіть випадково або зловмисно, передавши передбачуваний ключ на кшталт `"order-0001"`) заблокувати цей ключ для іншого користувача або дізнатися про факт його використання іншим покупцем (відсутній витік інформації через `422`).

### 2. Обмеження «не більше 4 квитків на користувача на подію» (ДЗ п. 15.4)
Умова «користувач не може мати більше 4 активних (`PENDING` або `PAID`) квитків на одну подію» охоплює кілька рядків у `Order` / `OrderItem`. Перевірка `SELECT count(*) ...` перед `INSERT` у `Read Committed` вразлива до *write skew*: два паралельні запити по 3 квитки обидва побачать `0 <= 4` і створять 6 квитків.

Порівняння трьох варіантів:

| Варіант | Як працює | Переваги | Недоліки |
|---|---|---|---|
| **А. Рівень ізоляції `Serializable` із повтором при `40001`** | Транзакція виконується з `isolationLevel: Prisma.TransactionIsolationLevel.Serializable`. Якщо два запити одного користувача паралельно читають його квитки й вставляють нові — PostgreSQL SSI кидає `40001`. | Не потребує змін у схемі БД. | Катастрофічне падіння пропускної здатності: через спільне оновлення `Event.availableSeats` конфлікти `40001` виникатимуть між **різними** користувачами тієї самої події. |
| **Б. `SELECT ... FOR UPDATE` на рядку `User` як точка серіалізації** | На початку `$transaction` виконується `SELECT id FROM "User" WHERE id = $userId FOR UPDATE`, після чого рахується `tx.orderItem.count({ where: { order: { userId, eventId, status: { in: ['PENDING', 'PAID'] } } } })`. | Не потребує нових таблиць; блокує **лише паралельні запити того самого користувача**, не зачіпаючи інших покупців події; залишається на швидкому `Read Committed`. | Блокує всі паралельні замовлення цього користувача навіть на *різні* події на час транзакції; потребує одного виклику `tx.$queryRaw` для `FOR UPDATE`. |
| **В. Денормалізований лічильник `UserEventQuota` з `CHECK (count <= 4)`** | Окрема таблиця `(userId, eventId, activeTickets)` з `PRIMARY KEY (userId, eventId)` та `CHECK ("activeTickets" >= 0 AND "activeTickets" <= 4)`. Оновлюється через `INSERT ... ON CONFLICT DO UPDATE SET activeTickets = activeTickets + $n WHERE activeTickets + $n <= 4`. | Цілком у дусі «перевірка й дія в одному атомарному операторі БД»; блокування гранулярне до пари `(userId, eventId)`. | Потребує нової таблиці в схемі та синхронного зменшення лічильника у всіх місцях виходу зі стану (`cancel`, `releaseExpired`, `refund`). |

**Обґрунтування вибору:**
Ми обираємо **Варіант Б (`SELECT ... FOR UPDATE` на рядку `User` на рівні `Read Committed`)**:
1. На початку транзакції `createWithHold` виконується `await tx.$queryRaw\`SELECT id FROM "User" WHERE id = ${input.userId}::uuid FOR UPDATE\``.
2. Оскільки всі паралельні запити одного й того самого користувача шикуються в чергу на його власному рядку `User`, наступний запит `tx.orderItem.count(...)` бачить уже зафіксований стан попереднього запиту цього користувача.
3. **Чим обраний Варіант Б гірший за інші:**
   - Гірший за **Варіант В (денормалізований лічильник)** тим, що серіалізує *всі* покупки конкретного користувача (навіть якщо він одночасно у двох вкладках купує квитки на дві різні події), а також покладається на дисципліну виклику `SELECT ... FOR UPDATE` у коді репозиторію, а не на декларативний `CHECK`-констрейнт у схемі таблиці.
   - Гірший за **Варіант А (`Serializable`)** тим, що розробник має явно пам'ятати, на якому батьківському рядку (`User`) брати песимістичне блокування для захисту інваріанта.

### 3. Чесна черга очікування (Waitlist) при звільненні місця (ДЗ п. 15.5)
Коли всі місця на подію розпродані або зарезервовані, і одне місце звільняється (через `cancel` або `releaseExpired`), роздавати його тому, хто випадково першим натисне кнопку в потрібну мілісекунду, нечесно і створює шквал polling-запитів від клієнтів.

**Рішення через `SELECT ... FOR UPDATE SKIP LOCKED`:**
1. Створюється таблиця черги очікування `WaitlistEntry`:
   - `id UUID PRIMARY KEY` (UUIDv7), `eventId UUID`, `userId UUID`, `status ('WAITING', 'FULFILLED', 'CANCELLED')`, `createdAt TIMESTAMPTZ(3)`
   - Індекс `@@index([eventId, status, createdAt, id])`.
2. Коли в `releaseSeats` місце звільняється (або у фоновому воркері розподілу вільних місць), замість простого переведення місця у `FREE` для всіх, транзакція бере найстаршу заявку з черги, яка зараз не обробляється іншим воркером:
   ```sql
   SELECT "id", "userId"
   FROM "WaitlistEntry"
   WHERE "eventId" = $1 AND "status" = 'WAITING'
   ORDER BY "createdAt" ASC, "id" ASC
   LIMIT 1
   FOR UPDATE SKIP LOCKED;
   ```
3. **Чому саме `FOR UPDATE SKIP LOCKED`:**
   - `ORDER BY "createdAt" ASC, "id" ASC` гарантує строгу справедливість FIFO (першим прийшов — першим отримав місце).
   - Якщо одночасно звільнилося 5 місць у 5 паралельних транзакціях, звичайний `FOR UPDATE` змусив би всі 5 транзакцій чекати на першу заявку в черзі. Модифікатор `SKIP LOCKED` наказує PostgreSQL миттєво пропустити рядки `WaitlistEntry`, які вже заблоковані паралельними транзакціями, і взяти наступного кандидата в черзі без очікування і без конфліктів.
   - Якщо черга порожня (запит повернув 0 рядків) — місце стандартно переводиться у `SeatStatus.FREE` і `availableSeats` збільшується на 1.
